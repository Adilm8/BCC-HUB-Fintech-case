# Спецификация требований: QR-платёж в магазине с частичным возвратом

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Код документа | BRS-QR-POS-2026-041 |
| Версия | 1.3 |
| Статус | На согласовании |
| Бизнес-заказчик | Департамент торгового эквайринга и расчётных продуктов |
| Автор | А. Сериков, старший бизнес-аналитик |

## 2. Цели и бизнес-ценность

- Обеспечить возможность оплаты покупок в розничных торговых точках через динамический QR-код без использования физической карты.
- Предоставить торговым точкам инструмент оформления частичного возврата стоимости отдельных позиций чека без полной отмены исходного QR-платежа.
- Сократить долю ручных претензионных обращений по возвратам в контакт-центр банка на 40% в течение 6 месяцев после запуска.
- Снизить время обслуживания клиента при возврате товара на кассе за счёт автоматизированного зачисления средств на исходный счёт.

## 3. Описание бизнес-процесса

### 3.1. Оплата покупки по QR-коду
1. Кассир формирует корзину на кассовом ПО и выбирает способ оплаты «QR-платёж».
2. POS-терминал запрашивает у банковского шлюза генерацию динамического QR-кода на итоговую сумму покупки.
3. Клиент сканирует QR-код в мобильном приложении банка и подтверждает списание средств.
4. Банковский шлюз возвращает подтверждение на терминал, после чего касса печатает фискальный чек.

### 3.2. Частичный возврат товара в торговой точке
1. Клиент обращается на кассу торговой точки с чеком и товаром, подлежащим частичному возврату.
2. Кассир находит исходный QR-платёж на POS-терминале, указывает сумму возвращаемых позиций и причину возврата.
3. Банковский сервис проверяет допустимость возврата, лимиты по сумме, количеству операций и сроку давности.
4. При успешной проверке выполняется зачисление средств клиенту и регистрация чека возврата в ОФД.
5. Кассир получает электронный чек возврата, а клиенту направляется уведомление о зачислении средств.

## 4. Функциональные требования

- **FR-01**: Система должна генерировать динамический QR-код стандарта EMVCo со сроком действия ровно 180 секунд с момента создания.
- **FR-02**: Оплата по QR-коду и последующие частичные возвраты выполняются исключительно в национальной валюте Республики Казахстан (KZT).
- **FR-03**: Минимальная сумма одного частичного возврата составляет 100,00 KZT; при меньшей сумме операция отклоняется с кодом `MIN_REFUND_AMOUNT_VIOLATION`.
- **FR-04**: Частичный возврат по успешно завершённому QR-платежу допускается оформить в течение 30 календарных дней с даты совершения исходной покупки.
- **FR-05**: По одному исходному QR-платежу допускается проведение не более 3 успешных частичных возвратов.
- **FR-06**: Суммарный объём всех частичных возвратов по одному QR-платежу не должен превышать сумму исходного платежа.
- **FR-07**: Для оформления частичного возврата на сумму свыше 50 000 KZT система должна запрашивать подтверждение 4-значным PIN-кодом кассира на терминале.
- **FR-08**: При выявлении подозрительной активности со стороны кассира или клиента система должна оперативно заблокировать операцию возврата и уведомить ответственного сотрудника в кратчайшие сроки.
- **FR-09**: Клиент вправе инициировать возврат (полный или частичный) в торговой точке только в пределах 14 календарных дней с даты проведения исходного QR-платежа.
- **FR-10**: При оформлении частичного возврата система последовательно отправляет запрос на зачисление средств в АБС и запрос на регистрацию фискального чека возврата в ОФД, после чего возвращает кассиру подтверждение.
- **FR-11**: Возврат средств по QR-платежу зачисляется исключительно на счёт или карту клиента, с которых выполнено списание.
- **FR-12**: После подтверждения возврата система должна распечатать бумажный слип на термопринтере, отправить push-уведомление клиенту с текстом «Возврат выполнен», выгрузить суточный реестр операций в CSV на SFTP-сервер бухгалтерии и обновить виджет выручки в личном кабинете директора магазина.
- **FR-13**: После возврата система формирует электронный чек с номером исходной транзакции, суммой возврата, остатком и временем операции с точностью до секунды.

## 5. Нефункциональные требования

- **NFR-01**: Время ответа сервиса частичного возврата (p95) не должно превышать 1500 мс при нагрузке до 120 запросов в секунду.
- **NFR-02**: Система должна обеспечивать высокую отказоустойчивость, мгновенную обработку возвратов и интуитивно понятный интерфейс кассира при любых пиковых нагрузках.
- **NFR-03**: Канал связи между POS-терминалом и банковским шлюзом должен защищаться протоколом TLS не ниже 1.2.

## 6. Требования к данным и аудиту

- **DR-01**: Записи о QR-платежах и частичных возвратах должны храниться не менее 5 лет согласно законодательству РК.
- **DR-02**: Для каждого исходного QR-платежа в базе данных должен поддерживаться актуальный остаток доступной для возврата суммы (`remainingAmount`), обновляемый в рамках атомарной транзакции.
- **DR-03**: Журнал аудита фиксирует ID кассира, ID терминала, время в ISO 8601 (UTC+5), сумму возврата и итоговый статус.

## 7. Интеграционные требования

- **IR-01**: Таймаут ответа от процессинга составляет 5 секунд; при его превышении ставится статус `PENDING_RECONCILIATION`.
- **IR-02**: API частичного возврата должно быть строго идемпотентным, чтобы повторная отправка того же запроса при сетевом сбое гарантированно не приводила к двойному зачислению средств клиенту.
- **IR-03**: Уведомление клиента о возврате передаётся в сервис нотификаций в течение 10 секунд после ответа АБС.
- **IR-04**: Правила сверки и клиринга частичных возвратов с Национальной платёжной системой (НПС): TBD — уточнить формат клирингового файла и расписание обмена у отдела расчётов.

## 8. Критерии приёмки

| ID | Сценарий проверки | Предусловия | Ожидаемый результат |
|---|---|---|---|
| AC-01 | Успешная оплата покупки по динамическому QR-коду | Корзина на 15 000,00 KZT, клиент авторизован | QR-код действует 180 сек., списание выполнено, напечатан чек |
| AC-02 | Первый частичный возврат на 5 000,00 KZT на 2-й день | Исходный QR-платёж на 15 000,00 KZT завершён | Возврат проведён, `remainingAmount = 10000.00`, клиент уведомлён |
| AC-03 | Второй частичный возврат на 3 000,00 KZT | Остаток по исходному платежу 10 000,00 KZT | Возврат проведён, `remainingAmount = 7000.00`, сформирован чек возврата |
| AC-04 | Частичный возврат на сумму 25 000,00 KZT | Исходный QR-платёж на 40 000,00 KZT | Так как сумма превышает 20 000 KZT, система запрашивает SMS-OTP менеджера торговой точки |
| AC-05 | Попытка возврата суммы выше доступного остатка | Остаток по исходному платежу 7 000,00 KZT | При запросе на 8 000,00 KZT операция отклоняется с ошибкой превышения остатка |

Приёмка функциональности считается завершённой при успешном прохождении сценариев AC-01 — AC-05.

## 10. Спецификация REST API: частичный возврат QR-платежа

### 10.1. Метод и URL

- **HTTP-метод**: `GET`
- **Endpoint**: `/api/v1/qr-payments/{paymentId}/refund`
- **Авторизация**: `Authorization: Bearer <pos_access_token>`
- **Формат тела запроса и ответа**: `application/json` (UTF-8)
- **Назначение**: Инициирует проведение частичного или полного возврата денежных средств по ранее завершённому QR-платежу.

### 10.2. Параметры запроса

| Параметр | Расположение | Тип | Обязательность | Допустимые значения / диапазон | Описание |
|---|---|---|---|---|---|
| `paymentId` | path | `integer` | Да | `1..999999999` | Идентификатор исходного QR-платежа |
| `amount` | body | `number` | Да | `100.00..5000000.00` | Сумма частичного возврата с двумя знаками после запятой |
| `isFullRefund` | body | `boolean` | Нет | `true`, `false` (по умолчанию `false`) | Признак полного возврата; при `isFullRefund = true` поле `amount` передавать запрещено |
| `currency` | body | `string` | Да | `KZT`, `USD`, `RUB` | Код валюты операции по ISO 4217 |
| `reasonCode` | body | `string` | Нет | `DAMAGED`, `WRONG_ITEM`, `CUSTOMER_REQUEST` | Код причины возврата товара |
| `cashierId` | body | `string` | Да | Длина `4..32` | Идентификатор кассира торговой точки |
| `terminalId` | body | `string` | Да | Длина `6..16` | Идентификатор POS-терминала |

### 10.3. Параметры ответа

| Поле | Тип | Обязательность | Формат / диапазон | Описание |
|---|---|---|---|---|
| `refundId` | `string` | Да | UUID v4 | Уникальный идентификатор операции возврата |
| `paymentId` | `string` | Да | UUID v4 | Идентификатор исходного QR-платежа |
| `refundSequence` | `integer` | Да | `1..5` | Порядковый номер частичного возврата (допускается до 5 возвратов по одному платежу) |
| `refundedAmount` | `number` | Да | `>= 100.00` | Фактически возвращённая сумма |
| `remainingAmount` | `number` | Да | `>= 0.00` | Оставшаяся доступная для возврата сумма по исходному платежу |
| `status` | `string` | Да | `COMPLETED`, `PENDING_RECONCILIATION`, `REJECTED` | Итоговый статус операции возврата |
| `processedAt` | `string` | Да | ISO 8601 (`UTC+5`) | Дата и время завершения обработки операции |

### 10.4. Коды ответов и примеры

| HTTP-код | Значение | Условие возврата |
|---|---|---|
| `201 Created` | Успех | Частичный возврат успешно зарегистрирован и проведён |
| `200 OK` | Бизнес-ошибка | Запрошенная сумма превышает доступный остаток (`INSUFFICIENT_REMAINING_AMOUNT`) |
| `400 Bad Request` | Ошибка валидации | Некорректные параметры запроса или сумма меньше 100,00 KZT (`MIN_REFUND_AMOUNT_VIOLATION`) |
| `401 Unauthorized` | Ошибка авторизации | Недействительный или истёкший токен POS-терминала |
| `504 Gateway Timeout` | Таймаут | Процессинг не ответил в течение 5 секунд |

Пример запроса:
```http
GET /api/v1/qr-payments/48291045/refund HTTP/1.1
Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.example
Content-Type: application/json

{
  "amount": 5000.00,
  "isFullRefund": false,
  "currency": "KZT",
  "reasonCode": "WRONG_ITEM",
  "cashierId": "CASH-1042",
  "terminalId": "POS-008412"
}
```

Пример успешного ответа (`201 Created`):
```json
{
  "refundId": "c1a7f310-7b2e-4f91-9e14-2b5c8d7a1023",
  "paymentId": "9f8c2a10-4b7d-4e21-8c3a-6d1e5b2f0a91",
  "refundSequence": 1,
  "refundedAmount": 5000.00,
  "remainingAmount": 10000.00,
  "status": "COMPLETED",
  "processedAt": "2026-11-20T14:35:12+05:00"
}
```

Пример ответа при превышении остатка (`200 OK`):
```json
{
  "status": "REJECTED",
  "errorCode": "INSUFFICIENT_REMAINING_AMOUNT",
  "message": "Запрошенная сумма превышает доступный остаток по исходному QR-платежу"
}
```

Пример ответа при ошибке валидации (`400 Bad Request`):
```json
{
  "status": "REJECTED",
  "errorCode": "MIN_REFUND_AMOUNT_VIOLATION",
  "message": "Минимальная сумма частичного возврата составляет 100,00 KZT"
}
```

### 10.5. Дополнительная логика обработки в смежных системах

В рамках обработки данного API-метода внешняя система лояльности «Банк-Бонус» обязана пересчитать квартальный кэшбэк-уровень клиента в таблице БД `loyalty_tiers_v2` и списать ранее начисленные бонусные баллы в ночном batch-задании в 03:00.
