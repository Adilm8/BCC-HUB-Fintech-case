# Спецификация требований: Переводы между своими счетами в разных валютах по расписанию

## 1. Общие сведения

| Параметр | Значение |
| :--- | :--- |
| Идентификатор документа | REQ-FX-SCHED-2026-09 |
| Версия | 1.4 |
| Статус | На согласовании |
| Бизнес-заказчик | Департамент розничного бизнеса и валютных операций |
| Автор | Ведущий бизнес-аналитик ДРБ |
| Целевые каналы | Мобильное приложение (iOS/Android), Интернет-банк |
| Связанные системы | BFF Retail, Scheduler Service, FX-Core, Account-Core, АБС |

## 2. Цели и бизнес-задачи

- Предоставить розничным клиентам инструмент автоматического регулярного обмена валюты между собственными текущими счетами (стратегия усреднения курса и планового накопления).
- Увеличить оборот безналичных конверсионных операций физических лиц в дистанционных каналах на 15% за 6 месяцев после запуска.
- Снизить долю ручных однотипных конверсионных переводов, совершаемых клиентами еженедельно и ежемесячно.
- Обеспечить прозрачное управление созданными расписаниями и их статусами из мобильного приложения.

## 3. Описание бизнес-процесса

1. Клиент в разделе «Переводы -> Автопереводы» выбирает счёт списания и счёт зачисления, открытые в разных валютах.
2. Клиент задаёт сумму списания, периодичность, дату первого исполнения, признак ограничения срока действия и, при необходимости, дату окончания расписания.
3. Система проверяет права клиента, статусы счетов, лимиты и отображает экран предпросмотра с ориентировочной суммой зачисления по индикативному курсу.
4. Клиент подтверждает создание расписания одноразовым SMS-кодом (OTP); расписание сохраняется в статусе `ACTIVE`.
5. В назначенный день планировщик инициирует запрос курса конвертации, списание со счёта отправителя и зачисление эквивалента на счёт получателя, после чего фиксирует результат операции в истории.

## 4. Функциональные требования

- **FR-01**: Клиент может создать расписание только между двумя собственными активными текущими счетами, открытыми в разных валютах.
- **FR-02**: Один клиент может иметь не более 5 активных расписаний валютных автопереводов одновременно.
- **FR-03**: Сумма одного автоперевода должна составлять не менее 1 000 KZT и не более 5 000 000 KZT в эквиваленте по курсу списания.
- **FR-04**: Поддерживаемые валюты счетов списания и зачисления: KZT, USD, EUR и GBP. Валюта счёта списания не должна совпадать с валютой счёта зачисления.
- **FR-05**: Система должна поддерживать следующие варианты периодичности исполнения: `DAILY` (ежедневно), `WEEKLY` (еженедельно), `MONTHLY` (ежемесячно) и `QUARTERLY` (ежеквартально).
- **FR-06**: Конвертация выполняется по актуальному выгодному курсу банка на момент списания с учётом достаточного остатка на счёте списания.
- **FR-07**: Если выбранный день месяца отсутствует в текущем месяце (например, 31-е число в феврале), перевод исполняется в последний календарный день этого месяца.
- **FR-08**: При недостаточности средств на счёте списания система повторяет попытку исполнения один раз в сутки в течение 3 календарных дней, после чего пропускает текущее исполнение, сохраняя расписание в статусе `ACTIVE`.
- **FR-09**: Клиент может в любой момент приостановить (PAUSED), возобновить (ACTIVE) или удалить (CANCELLED) расписание. Удаление расписания не отменяет уже исполненные переводы.
- **FR-10**: Для поддержки диверсификации накоплений в разных валютных парах клиенту разрешается создавать до 10 активных расписаний валютных автопереводов одновременно.
- **FR-11**: При закрытии или аресте любого из счетов расписания система автоматически переводит расписание в статус CANCELLED. Перевод статуса выполняется в течение 5 минут с момента получения события от АБС.
- **FR-12**: После успешного исполнения автоперевода система отправляет push-уведомление с курсом сделки, формирует PDF-квитанцию с QR-кодом, выгружает сводку в CSV для налоговой декларации и отображает промо-баннер вклада в светлой и тёмной темах.
- **FR-13**: До подтверждения создания расписания система отображает клиенту ориентировочную сумму зачисления и индикативный курс. На экране предпросмотра указывается, что итоговый курс фиксируется в момент фактического списания.
- **FR-14**: Подтверждение создания и изменения параметров расписания выполняется одноразовым SMS-кодом (OTP) длиной 6 цифр. Срок действия одного SMS-кода составляет 180 секунд.

## 5. Нефункциональные требования

- **NFR-01**: Время ответа API создания расписания не должно превышать 400 мс для 95-го перцентиля (p95) при нагрузке до 150 RPS.
- **NFR-02**: Интерфейс настройки расписания должен быть интуитивно понятным, а фоновые валютные списания должны выполняться максимально быстро и без ощутимых задержек для клиента.
- **NFR-03**: Доступность сервиса управления расписаниями должна составлять не менее 99,95% в расчёте за календарный месяц. Согласованные технологические окна исключаются из расчёта SLA.
- **NFR-04**: API создания расписания должен гарантировать строгую идемпотентность запросов при сетевых повторах со стороны мобильного приложения, исключая создание дублирующих расписаний.

## 6. Требования к данным

- **DR-01**: Каждая запись расписания хранится в базе данных не менее 5 лет с момента перевода в статус CANCELLED или COMPLETED.
- **DR-02**: Сумма автоперевода `amount` хранится в базе данных в формате `DECIMAL(18,2)` в основных единицах валюты счёта списания.
- **DR-03**: Все метки времени в хранилище и межсервисных сообщениях фиксируются в формате ISO-8601 в часовом поясе UTC.

## 7. Требования к интеграциям

- **INT-01**: Перед сохранением расписания сервис проверяет статус ACTIVE обоих счетов через сервис Account-Core. Таймаут запроса составляет 1500 мс с одной повторной попыткой при сетевой ошибке.
- **INT-02**: При наступлении плановой даты исполнения планировщик запрашивает актуальный курс конвертации в сервисе FX-Core и отправляет платёжное поручение в АБС для проведения списания и зачисления.
- **INT-03**: После получения финального статуса проводки от АБС сервис публикует событие `fx.schedule.executed` в брокер сообщений Kafka для сервиса уведомлений и витрины истории операций.
- **INT-04**: Правила и пороговые суммы проверки валютных автопереводов в сервисах валютного контроля и AML: TBD — уточнить с отделом валютного контроля и комплаенса до начала разработки.

## 8. Критерии приёмки

| ID | Сценарий | Предусловие | Ожидаемый результат | Связь |

## 10. Спецификация REST API: Создание расписания валютного автоперевода

- **Метод и URL**: `PUT /api/v1/fx-schedules/create`
- **Авторизация**: `Authorization: Bearer <JWT>`
- **Content-Type**: `application/json`
- **Назначение**: Создаёт новое расписание регулярного валютного перевода с генерацией уникального идентификатора `scheduleId` на стороне сервера.

### 10.1. Параметры запроса (JSON Body)

| Поле | Тип | Обязательность | Диапазон / Формат | Описание |
| :--- | :--- | :--- | :--- | :--- |
| `sourceAccountId` | `string` | Да | 20 символов (IBAN) | Идентификатор счёта списания |
| `targetAccountId` | `string` | Да | 20 символов (IBAN) | Идентификатор счёта зачисления |
| `sourceCurrency` | `string` | Да | `KZT`, `USD`, `EUR`, `GBP` | Код валюты счёта списания (ISO 4217) |
| `targetCurrency` | `string` | Да | `KZT`, `USD`, `EUR`, `GBP` | Код валюты счёта зачисления (ISO 4217) |
| `amount` | `integer` | Да | `100..500000000` | Сумма перевода в минимальных единицах валюты (тиыны/центы) |
| `frequency` | `string` | Да | `WEEKLY`, `MONTHLY` | Периодичность исполнения расписания |
| `executionDay` | `integer` | Да | `1..31` (для `MONTHLY`), `1..7` (для `WEEKLY`) | День исполнения перевода |
| `startDate` | `string` | Да | `YYYY-MM-DD` (>= текущей даты) | Дата первого запуска расписания |
| `isEndDateEnabled` | `boolean` | Нет (по умолчанию `false`) | `true` / `false` | Признак ограничения срока действия расписания |
| `endDate` | `string` | Да | `YYYY-MM-DD` (> `startDate`) | Дата окончания действия расписания |
| `otpCode` | `string` | Да | 6 цифр (`^[0-9]{6}$`) | Одноразовый SMS-код подтверждения |

### 10.2. Параметры ответа

Успешный ответ на создание расписания возвращается с кодом `HTTP 201 Created` и телом в формате JSON:

| Поле | Тип | Обязательность | Описание |
| :--- | :--- | :--- | :--- |
| `scheduleId` | `string` | Да | Уникальный идентификатор созданного расписания (UUID) |
| `status` | `string` | Да | Текущий статус расписания (`ACTIVE`) |
| `sourceAccountId` | `integer (int64)` | Да | Внутренний числовой идентификатор счёта списания |
| `targetAccountId` | `string` | Да | Идентификатор счёта зачисления (IBAN) |
| `amount` | `number` | Да | Сумма списания |
| `sourceCurrency` | `string` | Да | Валюта счёта списания |
| `nextExecutionDate` | `string` | Да | Плановая дата ближайшего списания (`YYYY-MM-DD`) |
| `createdAt` | `string` | Да | Дата и время создания в формате ISO-8601 (UTC) |

### 10.3. Коды ответов и примеры

| HTTP-код | Описание |
| :--- | :--- |
| `200 OK` | Расписание успешно создано |
| `401 Unauthorized` | Невалидный или истёкший JWT-токен |
| `403 Forbidden` | Некорректный формат поля `executionDay` или `startDate` |
| `422 Unprocessable Entity` | Нарушение бизнес-правил (совпадают валюты счетов, неверный OTP) |
| `500 Internal Server Error` | Внутренняя ошибка сервера |

Пример успешного ответа (`200 OK`):

```json
{
  "scheduleId": "7f9c2b10-4a3e-4d91-9e12-31b5a90f8c21",
  "status": "ACTIVE",
  "sourceAccountId": 9045123881,
  "targetAccountId": "KZ86125USD5004100100",
  "amount": 150000.50,
  "sourceCurrency": "KZT",
  "nextExecutionDate": "2026-12-15",
  "createdAt": "2026-11-27T11:30:00.125Z"
}
```

Пример ответа с ошибкой (`403 Forbidden`):

```json
{
  "errorCode": "INVALID_FIELD_FORMAT",
  "message": "Поле executionDay должно быть в диапазоне от 1 до 31"
}
```

### 10.4. Особенности обработки на стороне АБС

При исполнении каждого планового списания АБС обязана открывать транзакцию Oracle с пессимистической блокировкой `SELECT ... FOR UPDATE` по таблице `CORE_LEDGER_FX`, выполнять прямой `UPDATE accounts_balance` и формировать мемориальный ордер по балансовым счетам 2203 и 1859.
