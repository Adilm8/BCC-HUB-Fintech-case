## 2. Цели и бизнес-ценность

- Снизить финансовый ущерб от несанкционированного доступа к счетам клиентов за счёт оперативного информирования о входе с неизвестного устройства.
- Предоставить клиенту инструмент мгновенной реакции на подозрительный вход непосредственно из уведомления без звонка в контакт-центр.
- Обеспечить соответствие внутренним стандартам информационной безопасности и требованиям по аудиту событий аутентификации.

## 3. Описание процесса

1. Клиент проходит аутентификацию в мобильном приложении Alatau Mobile (логин/пароль, биометрия или PIN-код).
2. Сервис аутентификации проверяет отпечаток и идентификатор устройства в списке доверенных устройств клиента.
3. Если устройство отсутствует в списке доверенных, сервис аутентификации формирует событие входа с нового устройства и вызывает сервис уведомлений безопасности.
4. Сервис уведомлений безопасности формирует текст push-уведомления с параметрами сессии и направляет его через провайдеров доставки (APNs/FCM) на ранее зарегистрированные доверенные устройства клиента.
5. Клиент получает интерактивное push-уведомление с двумя кнопками действий: «Это я» и «Это не я».
6. В зависимости от выбранного действия система либо регистрирует новое устройство как доверенное, либо запускает процедуру реагирования на инцидент безопасности.

## 4. Функциональные требования

- **FR-01**: При успешной аутентификации клиента в мобильном приложении с устройства, идентификатор которого отсутствует в списке доверенных устройств клиента, система обязана сформировать событие входа с нового устройства и инициировать отправку push-уведомления.
- **FR-02**: Push-уведомление о входе с нового устройства должно содержать дату и время входа в формате ДД.ММ.ГГГГ ЧЧ:ММ (UTC+5), модель устройства, версию ОС и город, определённый по IP-адресу входа.
- **FR-03**: В тексте и заголовке push-уведомления запрещается отображать ИИН, полный номер телефона, реквизиты платёжных карт, остатки по счетам и одноразовые коды подтверждения.
- **FR-04**: Push-уведомление о входе с нового устройства относится к обязательным уведомлениям безопасности и не может быть отключено клиентом в настройках мобильного приложения.
- **FR-05**: Если вход выполнен с подозрительного устройства или из нетипичного региона, уведомление должно отображаться максимально заметно и доставляться незамедлительно с повышенным приоритетом.
- **FR-06**: При нажатии клиентом кнопки «Это я» система обязана добавить новое устройство в список доверенных устройств клиента и сохранить дату и время подтверждения в журнале аудита безопасности.
- **FR-07**: Клиент вправе в разделе «Настройки → Уведомления» отключить получение push-уведомлений о входе с нового устройства, если у него активирован канал SMS-информирования.
- **FR-08**: Если подтверждение доставки push-уведомления не получено в течение 30 секунд, система обязана автоматически направить резервное SMS-уведомление на основной номер телефона клиента.
- **FR-09**: Повторная отправка push-уведомления о входе с одного и того же устройства не должна выполняться чаще одного раза в 60 секунд в рамках одной клиентской сессии.
- **FR-10**: Срок жизни (TTL) push-уведомления о входе с нового устройства составляет ровно 300 секунд; по истечении этого времени не доставленное уведомление должно автоматически отменяться.
- **FR-11**: За отправку резервного SMS-уведомления при отказе канала push комиссия составляет 0 тенге для первых 5 сообщений в календарный месяц, а начиная с шестого сообщения — 15 руб. за каждое уведомление.
- **FR-12**: При нажатии клиентом кнопки «Это не я» система обязана немедленно завершить все активные сессии клиента, заблокировать доступ в мобильное приложение на 24 часа и направить событие инцидента в систему антифрода.

## 5. Нефункциональные требования

- **NFR-01**: Время от фиксации события входа с нового устройства в сервисе аутентификации до передачи запроса в шлюз push-уведомлений (APNs/FCM) не должно превышать 3 секунды для 99% запросов при нагрузке до 500 входов в секунду.
- **NFR-02**: Сервис уведомлений безопасности должен работать быстро, стабильно, легко масштабироваться под рост клиентской базы и обеспечивать интуитивно понятное отображение уведомлений.
- **NFR-03**: Записи журнала отправленных push-уведомлений и реакций клиента должны храниться в системе аудита не менее 5 лет с момента события.
- **NFR-04**: Коэффициент доступности сервиса уведомлений безопасности должен составлять не менее 99,95% в календарный месяц, за исключением согласованных технологических окон.

## 6. Требования к данным

- **DR-01**: Для каждого события входа с нового устройства в журнале аудита должны сохраняться: идентификатор события (UUID v4), идентификатор клиента, хэш отпечатка устройства (SHA-256), IP-адрес входа, время отправки и статус доставки.
- **DR-02**: Для хранения кэша доверенных устройств необходимо использовать Redis 7.2 Cluster с политикой вытеснения `allkeys-lru` и префиксом ключей `auth:trusted_dev:v2:`.
- **DR-03**: Передача персональных данных клиента и сетевых метаданных устройства между внутренними сервисами банка должна осуществляться исключительно по протоколу TLS 1.3 с взаимной аутентификацией (mTLS).

## 7. Требования к интеграциям

- **INT-01**: Сервис аутентификации обязан вызывать сервис уведомлений безопасности по протоколу HTTPS с таймаутом установки соединения 500 мс и таймаутом ожидания ответа 2000 мс.
- **INT-02**: Сервис уведомлений безопасности интегрируется со шлюзами APNs и FCM для отправки push-уведомлений и с корпоративным SMS-шлюзом для резервной доставки сообщений.
- **INT-03**: При получении реакции «Это не я» сервис уведомлений безопасности передаёт структурированное событие инцидента в систему антифрода в течение не более 5 секунд.
- **INT-04**: Интеграция с Huawei Mobile Services (HMS Push Kit) и схема маршрутизации для устройств без Google Mobile Services: TBD (будет определено на этапе технического проектирования).

## 8. Критерии приёмки

Проверка реализации выполняется по следующим основным функциональным сценариям:

| ID | Сценарий | Предусловие / Действие | Ожидаемый результат |
|---|---|---|---|
| AC-01 | Вход с нового устройства | Клиент входит с устройства, отсутствующего в списке доверенных | Отправлен push с датой/временем, моделью, ОС и городом входа |
| AC-02 | Подтверждение «Это я» | Клиент нажимает кнопку «Это я» в полученном уведомлении | Устройство добавлено в доверенные, действие записано в журнал аудита |
| AC-03 | Отказ «Это не я» | Клиент нажимает кнопку «Это не я» в полученном уведомлении | Завершается только сессия на новом устройстве; текущая сессия сохраняется, блокировка учётной записи не выполняется |
| AC-04 | Защита конфиденциальных данных | Сформирован push о входе с нового устройства | В тексте и заголовке отсутствуют ИИН, номер телефона, реквизиты карт и OTP |
| AC-05 | Резервная доставка SMS | Push не доставлен клиенту в течение 30 секунд | Система направляет резервное SMS-уведомление на номер клиента |
| AC-06 | Повторный вход | Повторный вход с того же устройства в той же сессии | Повторное push-уведомление не отправляется |

## 10. Спецификация REST API: Сервис уведомлений безопасности

### 10.1 Общие сведения

- **Метод и URL**: `POST /api/v1/security/login-push`
- **Протокол и аутентификация**: HTTPS (mTLS), обязательный заголовок `Authorization: Bearer <service_jwt>`
- **Формат обмена**: `application/json; charset=utf-8`
- **Идемпотентность**: Метод является строго идемпотентным: повторная отправка того же запроса не приводит к повторной отправке push-уведомления клиенту.
- **Коды ответа**: При успешной постановке уведомления в очередь отправки сервис возвращает HTTP-код `202 Accepted`, а при превышении лимита частоты отправки — `429 Too Many Requests`.
- **Обработка реакции «Это не я»**: Для обработки нажатия клиентом кнопки «Это не я» и немедленной блокировки учётной записи используется метод `GET /api/v1/security/sessions/block?client_id={client_id}&device_id={device_id}`.

### 10.2 Параметры запроса (`POST /api/v1/security/login-push`)

| Поле | Тип | Обязательность | Ограничения / Диапазон | Описание |
|---|---|---|---|---|
| client_id | string | Да | 1–32 символа, латиница и цифры | Внутренний идентификатор клиента в АБС |
| device_id | string (UUID) | Да | Формат UUID v4 (36 символов) | Уникальный идентификатор нового устройства |
| device_model | string | Да | 1–100 символов | Наименование модели устройства (например, iPhone 15) |
| os_version | string | Да | 1–32 символа | Название и версия ОС (например, iOS 17.5) |
| ip_address | string | Да | IPv4 или IPv6 | IP-адрес, с которого выполнен вход |
| city | string | Нет | 1–64 символа | Город входа, определённый по GeoIP |
| login_timestamp | string | Да | ISO-8601 (UTC+5) | Дата и время успешного входа |
| ttl | integer | Нет | 10–60 | Время жизни уведомления в минутах (по умолчанию 15) |
| risk_score | integer | Нет | 0–100 | Оценка риска входа от системы антифрода |
| sms_fallback_enabled | boolean | Нет | true / false (по умолчанию false) | Флаг включения резервной SMS-отправки |
| fallback_phone | string | Да | Формат E.164, 11–15 символов | Номер телефона для резервного SMS (передаётся только при sms_fallback_enabled = true) |

### 10.3 Параметры ответа

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| notification_id | string (UUID) | Да | Уникальный идентификатор созданного уведомления |
| device_id | integer (int64) | Да | Идентификатор устройства, на которое направлено уведомление |
| status | string | Да | Текущий статус обработки (`QUEUED`, `SENT`, `FAILED`) |
| created_at | string | Да | Дата и время регистрации запроса в формате ISO-8601 (UTC+5) |

Примечание по логике обработки: при получении `risk_score > 80` сервис уведомлений безопасности обязан самостоятельно пересчитать суточный лимит переводов клиента в АБС, перевести все карты клиента в процессинге Way4 в статус `SUSPECTED_FRAUD` и заблокировать подачу заявок на кредиты.

### 10.4 Коды ответов и примеры

**`201 Created`** — Уведомление успешно принято в очередь отправки:

```json
{
  "notification_id": "a7f3c9d0-12b4-4e8a-9c10-6f2e8a1b4c3d",
  "device_id": 904812345,
  "status": "QUEUED",
  "created_at": "2026-03-18T14:22:10+05:00"
}
```

**`400 Bad Request`** — Ошибка валидации параметров или превышение лимита частоты отправки (`RATE_LIMIT_EXCEEDED`):

```json
{
  "error_code": "RATE_LIMIT_EXCEEDED",
  "message": "Превышена допустимая частота отправки уведомлений для данного устройства"
}
```

**`401 Unauthorized`** — Отсутствует или недействителен токен авторизации `Bearer`:

```json
{
  "error_code": "UNAUTHORIZED",
  "message": "Недействительный сервисный токен авторизации"
}
```

**`500 Internal Server Error`** — Внутренняя ошибка сервиса уведомлений:

```json
{
  "error_code": "INTERNAL_ERROR",
  "message": "Внутренняя ошибка при постановке уведомления в очередь"
}
