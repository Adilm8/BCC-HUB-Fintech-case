# Спецификация требований: Возврат средств за отменённую покупку (Chargeback) — АРМ оператора

## 1. Общие сведения

| Параметр | Значение |
| :--- | :--- |
| Наименование функционала | Оформление и сопровождение возврата средств за отменённую покупку (chargeback) |
| Система / модуль | АРМ оператора «Претензионный центр» (модуль `claim-chargeback-core`) |
| Версия документа | 1.4 |
| Статус документа | На согласовании |
| Владелец продукта | Департамент претензионной работы и карточного сервиса |
| Целевые роли | Оператор первой линии (`CLAIM_OPERATOR`), руководитель группы (`CLAIM_SUPERVISOR`) |
| Связанные системы | Процессинговый шлюз МПС (Visa, Mastercard, «Мир»), АБС, Notification Hub, Антифрод |
| Плановый релиз | Q1 2027 |

## 2. Цели и бизнес-контекст

- Автоматизировать обработку клиентских обращений по возврату денежных средств за отменённые покупки в торгово-сервисных предприятиях (ТСП), по которым продавец не выполнил своевременный возврат.
- Сократить среднее время регистрации и первичной обработки претензионной заявки оператором до 6 минут за счёт интеграции АРМ с процессинговым шлюзом МПС.
- Обеспечить прозрачный аудит решений по возвратам и соблюдение регламентов платёжных систем по срокам оспаривания операций.

## 3. Описание процесса

1. Клиент обращается в контакт-центр или отделение банка с запросом на возврат средств по отменённой покупке и предоставляет подтверждающие документы (чек отмены, подтверждение от ТСП).
2. Оператор авторизуется в АРМ «Претензионный центр» и выполняет поиск исходной транзакции по данным клиента.
3. Оператор проверяет допустимость оспаривания, заполняет карточку заявки на возврат, выбирает код причины МПС и прикрепляет подтверждающие файлы.
4. Система регистрирует заявку, присваивает регистрационный номер и проверяет необходимость согласования руководителем группы.
5. При необходимости согласования заявка поступает в очередь руководителя (`CLAIM_SUPERVISOR`); после одобрения или при прохождении лимита оператором выполняется отправка диспута в МПС.
6. После получения результата обработки система переводит заявку в финальный статус и инициирует информирование клиента.
7. Все этапы обработки и изменения атрибутов заявки сохраняются в журнале аудита для последующего контроля и отчётности.

## 4. Функциональные требования

- **FR-01.** Оператор должен иметь возможность выполнить поиск исходной карточной транзакции клиента по её уникальному идентификатору, маскированному номеру карты (формат 6+4) или дате и сумме операции за последние 180 календарных дней.
- **FR-02.** Оператор имеет право инициировать заявку на возврат (chargeback) по отменённой покупке в течение 60 календарных дней с даты совершения исходной транзакции.
- **FR-03.** При создании заявки на возврат система обязана присваивать ей уникальный регистрационный номер формата `CHB-YYYYMMDD-XXXXXX` и фиксировать дату и время регистрации в часовом поясе UTC+3.
- **FR-04.** При получении обращения клиента оператор должен оперативно проверить корректность подтверждающих документов и при необходимости запросить дополнительные материалы в разумный срок.
- **FR-05.** Оператор должен иметь возможность прикрепить к заявке до 5 подтверждающих документов клиента в форматах PDF, JPEG или PNG размером не более 10 МБ каждый.
- **FR-06.** При подтверждении оператором решения о возврате система направляет запрос на списание в процессинговый шлюз МПС, переводит заявку в статус `SENT_TO_IPS` и зачисляет сумму возврата на счёт клиента.
- **FR-07.** Заявки на возврат по транзакциям старше 45 календарных дней с даты списания автоматически отклоняются системой без возможности передачи в работу оператору.
- **FR-08.** Система должна формировать печатную форму уведомления об отказе в формате PDF, автоматически пересчитывать KPI смены оператора в витрине отчётности и архивировать переписку с торговой точкой в корпоративное хранилище.
- **FR-09.** Система должна поддерживать как полный, так и частичный возврат средств по отменённой покупке в размере от 1% до 100% суммы исходной транзакции.
- **FR-10.** Если сумма возврата превышает 50 000 RUB (либо эквивалент в валюте счёта по курсу ЦБ РФ на дату регистрации заявки), заявка должна направляться на обязательное согласование руководителю группы (`CLAIM_SUPERVISOR`) перед отправкой в МПС.
- **FR-11.** Все действия оператора по изменению статуса, суммы или комментария заявки должны фиксироваться в журнале аудита с указанием идентификатора пользователя, временной метки (UTC) и предыдущего/нового значения поля.
- **FR-12.** При переводе заявки в финальный статус (`APPROVED`, `REJECTED` или `CANCELLED`) система обязана в течение 5 минут направить клиенту push-уведомление и SMS-сообщение с номером заявки и принятым решением.

## 5. Нефункциональные требования

- **NFR-01.** Время ответа сервиса при поиске транзакции и открытии карточки заявки не должно превышать 1,5 секунды для 95-го перцентиля (p95) при нагрузке до 120 RPS.
- **NFR-02.** Интерфейс АРМ оператора должен быть интуитивно понятным, удобным в ежедневной работе и обеспечивать быстрый отклик при высокой нагрузке без заметных задержек.
- **NFR-03.** Доступность модуля обработки возвратов в рабочее время контакт-центра (07:00–23:00 МСК) должна составлять не менее 99,9% в календарный месяц, при этом допустимое время планового простоя не превышает 30 минут в ночное окно (02:00–05:00 МСК).
- **NFR-04.** Полный номер банковской карты (PAN) не должен отображаться в интерфейсе АРМ оператора и записываться в прикладные логи в открытом виде; допускается маскирование формата `XXXXXX******XXXX` в соответствии со стандартом PCI DSS.

## 6. Требования к данным

- **DR-01.** Все зарегистрированные заявки на возврат, приложенные скан-копии документов и записи журнала аудита должны храниться в системе не менее 5 лет с даты закрытия заявки в соответствии с требованиями архивного хранения банка.
- **DR-02.** Все денежные суммы при хранении и межсистемном обмене передаются в минимальных единицах валюты (копейках/центах, тип `integer`), а коды валют — строго по стандарту ISO 4217 (например, `RUB`).
- **DR-03.** Справочник кодов причин возврата (reason codes) МПС Visa, Mastercard и «Мир» должен храниться в нормализованном виде с указанием кода, наименования, признака активности и срока действия правила.

## 7. Интеграционные требования

- **IR-01.** Взаимодействие между АРМ оператора и бэкенд-сервисом «Претензионный центр» должно осуществляться по протоколу HTTPS (TLS 1.2 и выше) с аутентификацией пользователя на основе OAuth 2.0 / JWT и проверкой роли `CLAIM_OPERATOR` или `CLAIM_SUPERVISOR`.
- **IR-02.** Интеграция с сервисом уведомлений (Notification Hub) осуществляется асинхронно через брокер сообщений Apache Kafka (топик `claim.notifications.v1`) с гарантией доставки не ниже at-least-once.
- **IR-03.** Интеграция с процессинговым шлюзом МПС выполняется по защищённому каналу mTLS с использованием стандартного шлюзового адаптера претензионных диспутов.
- **IR-04.** Порядок обмена сообщениями с антифрод-системой и перечень стоп-факторов для блокировки возврата — TBD (уточнить у подразделения комплаенс и информационной безопасности до этапа разработки).

## 10. Спецификация REST API: Регистрация возврата (Chargeback)

### 10.1. Метод и URL

- **Метод и URL:** `GET /api/v1/chargebacks/create` (тело запроса передаётся в формате `application/json`)
- **Заголовки запроса:** `Authorization: Bearer <JWT>`, `Content-Type: application/json`
- **Идемпотентность:** Эндпоинт гарантирует строгую идемпотентность повторных вызовов в течение 24 часов: повторный запрос оператора не создаёт дубликат возврата.

### 10.2. Параметры запроса (JSON Body)

| Поле | Тип | Обязательный | Диапазон / формат | Описание |
| :--- | :--- | :--- | :--- | :--- |
| transactionId | string | Да | UUID v4 (36 символов) | Уникальный идентификатор исходной транзакции |
| refundAmount | decimal | Да | 0.01–500000.00 | Сумма возврата в рублях (с точностью до двух знаков) |
| currency | string | Да | 3 символа | Код валюты операции (например, `RUR`) |
| reasonCode | string | Да | 2–8 символов | Код причины оспаривания МПС (например, `13.1`) |
| isMerchantNotified | boolean | Нет | `true` / `false` (по умолчанию `false`) | Признак предварительного обращения клиента в ТСП |
| merchantNotificationDate | string | Да | `YYYY-MM-DD` | Дата уведомления ТСП; заполняется только если `isMerchantNotified = true` |
| operatorComment | string | Нет | до 1000 символов | Комментарий оператора к заявке |

**Правила валидации параметров:**
- Сумма возврата (`refundAmount`) должна строго равняться полной сумме исходной транзакции; частичный возврат через API не поддерживается.

### 10.3. Структура ответа (JSON)

| Поле | Тип | Обязательный | Описание |
| :--- | :--- | :--- | :--- |
| claimNumber | string | Да | Регистрационный номер заявки (`CHB-YYYYMMDD-XXXXXX`) |
| transactionId | integer (int64) | Да | Идентификатор исходной транзакции |
| reasonCode | integer | Да | Числовой код причины оспаривания |
| status | string | Да | Текущий статус заявки (`CREATED`, `PENDING_APPROVAL`, `SENT_TO_IPS`) |
| refundAmount | decimal | Да | Подтверждённая сумма возврата |
| createdAt | string (ISO 8601) | Да | Дата и время регистрации заявки (UTC+3) |

### 10.4. Логика взаимодействия с АБС

При успешной регистрации заявки на возврат АБС должна выполнить SQL-процедуру `SP_CREATE_GL_MEMO`, сформировать парные проводки по счетам 47422/40817 в схеме `CBS_CORE` и обновить таблицу `GL_DAILY_BALANCES` в рамках распределённой XA-транзакции.

### 10.5. Коды ответов и примеры

| HTTP-код | Описание |
| :--- | :--- |
| 200 OK | Заявка на возврат успешно создана |
| 400 Bad Request | Некорректный синтаксис JSON или формат полей запроса |
| 401 Unauthorized | Отсутствует или недействителен JWT-токен |
| 403 Forbidden | Недостаточно прав доступа у текущей роли |
| 404 Not Found | Исходная транзакция не найдена |
| 422 Unprocessable Entity | Нарушение бизнес-правил оформления возврата |

**Пример успешного ответа (`HTTP/1.1 200 OK`):**
```json
{
  "claimNumber": "CHB-20261127-004812",
  "transactionId": 984512034,
  "reasonCode": 131,
  "status": "CREATED",
  "refundAmount": 1500.50,
  "createdAt": "2026-11-27T14:25:10+03:00"
}
```

**Пример ответа при ошибке — исходная транзакция не найдена (`HTTP/1.1 200 OK`):**
```json
{
  "status": "ERROR",
  "errorCode": "TXN_NOT_FOUND",
  "message": "Исходная транзакция не найдена"
}
