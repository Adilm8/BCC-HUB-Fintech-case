- **Раздел:** Часть A. Новый функционал › Дизайн процесса UI · **Тип:** Интерфейс пользователя (UI)
- **Затронуто в наборе:** S-006

- **[Незначительный] D-001** (ISO/IEC/IEEE 29148:2018, п. 5.2.5 — полнота): «При ошибке ввода сообщение появляется под полем» — Не заданы условия ошибки (пусто, не число, вне 1 000–1 000 000, дробное) и тексты сообщений. API отдаёт разные варианты: 200 с «Проверьте сумму» и 400 «Некорректный запрос». Тест на текст и момент показа не написать. Рекомендация: Перечислить условия ошибки и тексты сообщений для каждой, указать, делается ли проверка на клиенте. Вопрос: Откуда берётся текст сообщения под полем «Порог, ₸»: задаётся на клиенте для каждого правила (пусто, не число, вне диапазона) или берётся из message ответа сервера?

#### [Существенный] D-003 — Однозначность

- **Критерий:** ISO/IEC/IEEE 29148:2018, п. 5.2.5 — однозначность
- **Источник:** семантический анализ
- **Раздел:** Часть A. Новый функционал › Требования к изменениям › Функциональные требования
- **Цитата** (*подтверждена дословно*):
  > В расходы входят проведённые покупки
- **Объяснение:** «Проведённые» не определено: неясно, учитываются ли авторизованные, но не проведённые суммы, отменённые авторизации и операции в иностранной валюте. В какой валюте и по какому курсу суммируются такие покупки, не сказано. Счётчик и момент push будут отличаться между реализациями.
- **Рекомендация:** Определить статусы операций, входящие в расход, и валюту и курс для покупок не в тенге.
- **Уточняющий вопрос** (Бизнес / Product Owner): Какое событие процессинга (авторизация или проведение) считается покупкой для расчёта порога и в какой сумме учитываются покупки в иностранной валюте?
- **Варианты ответа:**
  - Только окончательно проведённые, сумма списания в тенге
    - *Что изменится:* Определение «проведённые» фиксируется, статус ожидания игнорируется
  - Также авторизованные (удержанные) суммы до проводки

### Проверка цитат и отсев находок

Каждая находка проходит детерминированную сверку цитат по тексту документа (нормализация, точное совпадение, затем нечёткое сопоставление с заменой на дословный фрагмент документа). Находки без подтверждённой цитаты отбрасываются.

Цитаты в итоговых нарушениях (у одного нарушения может быть несколько цитат):

- Цитаты, совпавшие с текстом дословно (`verified`): 89
- Цитаты, исправленные по тексту документа (`repaired`): 0
- Цитаты, заменённые текстом требования (`anchored`): 0

Находки (кандидаты в нарушения):

- Отброшено находок без подтверждённой цитаты: 0
- Отброшено на этапе критического пересмотра: 3
- Объединено с другими находками как дубли: 45
- Не подтверждено критиком (цитата только по тексту требования): 0

Баланс кандидатов: всего 96 (правила — 21, проверка каждого требования — 50, проверка набора — 24, сводные находки по матрице покрытия — 1) = итоговые нарушения 48 + объединённые дубли 45 + удалённые критиком 3 + неподтверждённые 0. Находки без подтверждённой цитаты (0) отброшены до попадания в кандидаты.

### Ограничения

- Выполняется только статический анализ текста спецификации без доступа к исходному коду, базам данных и внешним системам.
- Встроенные изображения, схемы и диаграммы в графическом формате не анализируются.
- Бизнес-корректность требований, приоритеты и выбор между противоречащими формулировками требуют подтверждения со стороны автора ТЗ.
