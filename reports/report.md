### R-003 (присвоен агентом) — Интерфейс раздела настроек уведомлений

- **Раздел:** Часть A. Новый функционал › Дизайн процесса UI · **Тип:** Интерфейс пользователя (UI)

#### [Существенный] D-001 — Полнота

- **Критерий:** ISO/IEC/IEEE 29148:2018, п. 5.2.5 — полнота
- **Источник:** семантический анализ
- **Раздел:** Часть A. Новый функционал › Дизайн процесса UI
- **Цитата** (*подтверждена дословно*):
  > При ошибке ввода сообщение появляется под полем
- **Объяснение:** Не указан конкретный текст сообщения об ошибке и точные условия его вывода под полем, из-за чего тестировщик не сможет написать тест с ожидаемым результатом, а разработчик — реализовать валидацию.
- **Рекомендация:** Уточнить текст и условия отображения ошибки валидации под полем ввода.
- **Уточняющий вопрос** (Бизнес / Product Owner): Каков точный текст сообщения об ошибке, выводящийся под полем ввода при некорректном пороге?
- **Варианты ответа:**
  - «Введите целое число от 1 000 до 1 000 000 ₸»
    - *Что изменится:* Отображать понятную подсказку с допустимым диапазоном значений.
  - «Некорректная сумма порога»
    - *Что изменится:* Отображать общее сообщение о некорректной сумме.

- **Раздел:** Часть A. Новый функционал › Требования к изменениям › Функциональные требования
- **Цитата** (*подтверждена дословно*):
  > Держатель активной карты KZT задаёт целый порог
- **Объяснение:** Не описано поведение системы, если клиент пытается задать порог для заблокированной/неактивной карты или карты в иной валюте (USD/EUR), что оставляет неопределённость в UI и API.
- **Рекомендация:** Добавить сценарий обработки неактивных карт и карт с валютой, отличной от KZT.
- **Уточняющий вопрос** (Бизнес / Product Owner): Как система должна отвечать в интерфейсе и API при попытке установить порог для неактивной карты или карты в валюте, отличной от KZT?
- **Варианты ответа:**
  - Скрывать экран/настройку в UI и возвращать ошибку в API
    - *Что изменится:* Недоступность раздела для не подходящих под условия карт.
  - Отображать экран в режиме только для чтения с информером
    - *Что изменится:* Отображение блокирующего сообщения в интерфейсе.

- **Противоречивые** (5):

  - **S-002** (Часть A. ### Проверка цитат и отсев находок

Каждая находка проходит детерминированную сверку цитат по тексту документа (нормализация, точное совпадение, затем нечёткое сопоставление с заменой на дословный фрагмент документа). Находки без подтверждённой цитаты отбрасываются.

Цитаты в итоговых нарушениях (у одного нарушения может быть несколько цитат):

- Цитаты, совпавшие с текстом дословно (`verified`): 50
- Цитаты, исправленные по тексту документа (`repaired`): 0
- Цитаты, заменённые текстом требования (`anchored`): 0

Находки (кандидаты в нарушения):

- Отброшено находок без подтверждённой цитаты: 0
- Отброшено на этапе критического пересмотра: 1
- Объединено с другими находками как дубли: 23
- Не подтверждено критиком (цитата только по тексту требования): 0

Баланс кандидатов: всего 54 (правила — 20, проверка каждого требования — 18, проверка набора — 15, сводные находки по матрице покрытия — 1) = итоговые нарушения 30 + объединённые дубли 23 + удалённые критиком 1 + неподтверждённые 0. Находки без подтверждённой цитаты (0) отброшены до попадания в кандидаты.

### Ограничения

- Выполняется только статический анализ текста спецификации без доступа к исходному коду, базам данных и внешним системам.
- Встроенные изображения, схемы и диаграммы в графическом формате не анализируются.
- Бизнес-корректность требований, приоритеты и выбор между противоречащими формулировками требуют подтверждения со стороны автора ТЗ.
