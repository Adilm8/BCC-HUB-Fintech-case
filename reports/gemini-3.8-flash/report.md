### Что исправить первым

1. **S-003** — Критерий приёмки прямо противоречит требованию Ф-2 (R-010), где указано: «Месяц определяется по дате совершения покупки в Алматы»
2. **S-004** — Требование Ф-3 устанавливает абсолютное ограничение не более одного push на карту в календарный месяц, тогда как Ф-4 предписывает отправлять push при очередном превышении после смены порога независимо от предшествующих событий
3. **S-001** — В требовании заявлено, что приложение выполняет чтение и сохранение настроек через REST API, однако в дочерней спецификации Части B представлен только метод сохранения (/alerts/saveLimit) с обязательными параметрами суммы и статуса, а эндпоинт для чтения настроек отсутствует
4. **S-006** — В разделе «Часть B. REST API › Ответ» упоминается HTTP-статус 201, однако в перечне объявленных статусов (200, 400, 401, 403, 500) он отсутствует
5. **S-005** — Требование позиционирует код 200 как ответ в случае успешного выполнения метода, однако далее в примере блока R-058 в рамках кода 200 приводится сценарий ошибки с телом {"result":"ERROR","message":"Проверьте сумму"}
6. **S-002** — В функциональных требованиях Ф-1, дизайне интерфейса и параметрах API предусмотрен признак включения уведомления (enabled), но в схеме BPMN и Sequence Diagram проверка этого флага полностью отсутствует
7. **S-007** — Требование предписывает возвращать статус 404 для чужой карты, однако оно размещено внутри подраздела «403. Unsuccessful — Forbidden», а статус 403 при этом заявлен в общем перечне (R-058), но сценарий его возврата нигде не описан
8. **D-012** — Использование метода GET для операции сохранения и изменения настроек порога нарушает стандарт HTTP и принципы REST, согласно которым метод GET должен быть безопасным и не изменять состояние сервера
9. **D-017** — Передача идентификатора карты (cardId) и финансового порога (amount) в параметрах строки запроса (Query) приводит к компрометации данных в журналах веб-серверов, прокси-серверах и истории переходов, что нарушает правила информационной безопасности

### Проверка цитат и отсев находок

Каждая находка проходит детерминированную сверку цитат по тексту документа (нормализация, точное совпадение, затем нечёткое сопоставление с заменой на дословный фрагмент документа). Находки без подтверждённой цитаты отбрасываются.

Цитаты в итоговых нарушениях (у одного нарушения может быть несколько цитат):

- Цитаты, совпавшие с текстом дословно (`verified`): 77
- Цитаты, исправленные по тексту документа (`repaired`): 0
- Цитаты, заменённые текстом требования (`anchored`): 0

Находки (кандидаты в нарушения):

- Отброшено находок без подтверждённой цитаты: 0
- Отброшено на этапе критического пересмотра: 2
- Объединено с другими находками как дубли: 36
- Не подтверждено критиком (цитата только по тексту требования): 0

Баланс кандидатов: всего 87 (правила — 24, проверка каждого требования — 38, проверка набора — 24, сводные находки по матрице покрытия — 1) = итоговые нарушения 49 + объединённые дубли 36 + удалённые критиком 2 + неподтверждённые 0. Находки без подтверждённой цитаты (0) отброшены до попадания в кандидаты.

### Ограничения

- Выполняется только статический анализ текста спецификации без доступа к исходному коду, базам данных и внешним системам.
- Встроенные изображения, схемы и диаграммы в графическом формате не анализируются.
- Бизнес-корректность требований, приоритеты и выбор между противоречащими формулировками требуют подтверждения со стороны автора ТЗ.
- Предупреждение прогона: Доменный профиль banking выбран автоматически: основ найдено 9, вхождений 44.
- Предупреждение прогона: Ответ нарезчика обрезан: часть блоков отнесена к требованиям правилами.
