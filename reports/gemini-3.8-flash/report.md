#### [Существенный] D-001 — Полнота

- **Критерий:** ISO/IEC/IEEE 29148:2018, п. 5.2.5 — полнота
- **Источник:** семантический анализ
- **Раздел:** Часть A. Новый функционал › Дизайн процесса UI
- **Цитата** (*подтверждена дословно*):
  > На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»
- **Объяснение:** Не определено состояние поля «Порог, ₸» и кнопки «Сохранить», если переключатель находится в выключенном состоянии (блокируются ли они, скрываются или остаются доступными для редактирования).
- **Рекомендация:** Уточнить поведение и визуальное состояние поля ввода порога и кнопки «Сохранить» при выключенном тумблере уведомлений.
- **Уточняющий вопрос** (Бизнес / Product Owner): Как должны отображаться и вести себя поле «Порог, ₸» и кнопка «Сохранить», если переключатель уведомлений выключен?
- **Варианты ответа:**
  - Поле ввода и кнопка блокируются (disabled)
    - *Что изменится:* Разработчик UI блокирует элементы формы при неактивном тумблере.
  - Блок настройки порога скрывается с экрана
    - *Что изменится:* Разработчик UI скрывает блок ввода порога при отключении уведомлений.
  - Поле и кнопка остаются активными для предварительной настройки
    - *Что изменится:* Пользователь может настроить и сохранить порог до включения уведомлений.

- **[Незначительный] D-002** (ISO/IEC/IEEE 29148:2018, п. 5.2.5 — полнота): «При ошибке ввода сообщение появляется под полем» — В требовании не указан конкретный текст сообщения об ошибке валидации ввода и условия его вывода (при пустом поле, нечисловых символах или сумме вне диапазона 1 000–1 000 000 ₸), из-за чего разработчик UI и тестировщик не знают точные формулировки и критерии проверки. Рекомендация: Указать точный текст сообщения об ошибке под полем для каждого случая некорректного ввода. Вопрос: Какой текст сообщения об ошибке должен отображаться под полем при невалидном вводе порога?

- **Раздел:** Часть A. Новый функционал › Требования к изменениям › Функциональные требования
- **Цитата** (*подтверждена дословно*):
  > По умолчанию уведомление выключено
- **Объяснение:** Не указано значение порога по умолчанию (предзаполненная сумма в поле ввода), когда клиент впервые включает уведомление, из-за чего разработчики UI могут оставить поле пустым или установить произвольную величину.
- **Рекомендация:** Указать стартовое значение порога при первом включении функции (например, плейсхолдер или минимальная сумма 1 000 ₸).

2. **S-004** — Требование Ф-3 жестко ограничивает количество push-уведомлений одним за календарный месяц на карту, тогда как требование Ф-4 предписывает отправить push при достижении нового порога независимо от ранее отправленных уведомлений
3. **S-008** — В перечне статусов статус 403 зафиксирован для запрета доступа к ресурсу, однако в пояснении к подразделу 403 сказано, что для чужой карты возвращается 404, как и для отсутствующей
4. **S-007** — Пример ответа под успешным заголовком «200. Successful — Created» (200) содержит признак ошибки ("result": "ERROR"), тогда как для некорректных параметров в спецификации отдельно объявлен код 400
5. **S-002** — Бизнес-правило Ф-1 строго ограничивает установку порога только активными картами в валюте KZT
6. **S-001** — Бизнес-цель R-001 формулирует ценность как информирование «в момент покупки» (во время авторизации), тогда как функциональное требование Ф-2 включает в расходы только «проведённые покупки» (финансовое списание/клиринг)
7. **S-005** — В документе полностью отсутствует спецификация межсервисного (M2M) интерфейса между сервисом расходов и сервисом настроек
8. **S-006** — В разделе «Часть B. REST API › Общие параметры» указан безопасный HTTP-метод GET, однако описание операции «Сохранение» указывает на операцию изменения данных (RFC 9110)
9. **S-009** — В дочерней спецификации API описан только метод сохранения порога (/alerts/saveLimit)
10. **D-009** — Для отправки push передаются только последние четыре цифры карты и сумма, но не передается идентификатор адресата (userId, client_id или deviceToken), из-за чего сервис push не сможет определить получателя сообщения

### Проверка цитат и отсев находок

Каждая находка проходит детерминированную сверку цитат по тексту документа (нормализация, точное совпадение, затем нечёткое сопоставление с заменой на дословный фрагмент документа). Находки без подтверждённой цитаты отбрасываются.

Цитаты в итоговых нарушениях (у одного нарушения может быть несколько цитат):

- Цитаты, совпавшие с текстом дословно (`verified`): 72
- Цитаты, исправленные по тексту документа (`repaired`): 0
- Цитаты, заменённые текстом требования (`anchored`): 0

Находки (кандидаты в нарушения):

- Отброшено находок без подтверждённой цитаты: 0
- Отброшено на этапе критического пересмотра: 1
- Объединено с другими находками как дубли: 40
- Не подтверждено критиком (цитата только по тексту требования): 0

Баланс кандидатов: всего 83 (правила — 21, проверка каждого требования — 38, проверка набора — 22, сводные находки по матрице покрытия — 1, добавлено критиком — 1) = итоговые нарушения 42 + объединённые дубли 40 + удалённые критиком 1 + неподтверждённые 0. Находки без подтверждённой цитаты (0) отброшены до попадания в кандидаты.

### Ограничения

- Выполняется только статический анализ текста спецификации без доступа к исходному коду, базам данных и внешним системам.
- Встроенные изображения, схемы и диаграммы в графическом формате не анализируются.
- Бизнес-корректность требований, приоритеты и выбор между противоречащими формулировками требуют подтверждения со стороны автора ТЗ.
- Предупреждение прогона: Доменный профиль banking выбран автоматически: основ найдено 9, вхождений 44.
