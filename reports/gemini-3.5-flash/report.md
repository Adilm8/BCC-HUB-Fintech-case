### R-006 (Ф-1) — Настройка лимита по активной карте

#### [Существенный] D-002 — Полнота

- **Критерий:** ISO/IEC/IEEE 29148:2018, п. 5.2.5 — полнота
- **Источник:** семантический анализ
- **Раздел:** Часть A. Новый функционал › Требования к изменениям › Функциональные требования
- **Цитата** (*подтверждена дословно*):
  > По умолчанию уведомление выключено
- **Объяснение:** Не указано значение порога по умолчанию при первом включении уведомления пользователем, если он сам его ещё не вводил. Разработчик не сможет инициализировать поле на экране или в БД.
- **Рекомендация:** Указать значение порога по умолчанию при первом включении.
- **Уточняющий вопрос** (Системный аналитик / API): Какое значение порога расходов по умолчанию должно отображаться на UI и храниться в БД при первом включении уведомлений клиентом?
- **Варианты ответа:**
  - Минимальное значение диапазона (1 000 ₸)
    - *Что изменится:* Установить дефолтное значение 1 000 ₸ в БД и на форме
  - Среднее или фиксированное значение (например, 50 000 ₸)
    - *Что изменится:* Установить дефолтное значение 50 000 ₸
  - Поле ввода должно быть пустым, требуя обязательного ввода от пользователя
    - *Что изменится:* Сделать поле пустым и не сохранять форму без ввода порога

### R-007 (Ф-2) — Правила расчета расходов

- **Раздел:** Часть A. Новый функционал › Требования к изменениям › Функциональные требования · **Тип:** Функциональное
- **Затронуто в наборе:** S-001, S-002, S-012

#### [Существенный] D-003 — Полнота

- **Критерий:** ISO/IEC/IEEE 29148:2018, п. 5.2.5 — полнота
- **Источник:** семантический анализ
- **Раздел:** Часть A. Новый функционал › Требования к изменениям › Функциональные требования
- **Цитата** (*подтверждена дословно*):
  > Возврат уменьшает расходы месяца исходной покупки
- **Объяснение:** Не описано поведение при частичном возврате и в случае, когда исходная покупка не найдена в базе данных (например, совершена до внедрения системы). Разработчик не сможет корректно рассчитать уменьшение расходов.
- **Рекомендация:** Добавить правила обработки частичных возвратов и возвратов по неопознанным покупкам.
- **Уточняющий вопрос** (Системный аналитик / API): Каковы правила пересчета расходов при получении частичного возврата или возврата по операции, оригинальная покупка по которой отсутствует в базе данных (например, совершена до старта функционала)?

### Противоречия

#### [Критичный] S-001 — Противоречие

- **Критерий:** ISO/IEC/IEEE 29148:2018, п. 5.2.6 — согласованность набора
- **Источник:** критический пересмотр
- **Затронутые требования:** R-002, R-007
- **Подтверждающие цитаты:**
  1. Раздел: Часть A. Новый функционал › Цели, требование `R-002` (*подтверждена дословно*)
     > Дать клиенту возможность узнать о достижении личного бюджета в момент покупки
  2. Раздел: Часть A. Новый функционал › Требования к изменениям › Функциональные требования, требование `R-007` (*подтверждена дословно*)
     > В расходы входят проведённые покупки
- **Объяснение:** Существует фундаментальное противоречие между бизнес-целью информирования клиента прямо 'в момент покупки' и правилом учета расходов исключительно по клиринговым 'проведённым' транзакциям. Из-за этого разработчики и тестировщики не смогут согласовать триггер отправки push-уведомления: либо уведомление будет приходить с огромной задержкой, либо расчет будет некорректным относительно официальной выписки. Пример: Клиент расплачивается картой в торговой точке. Система пересчитывает сумму расходов по карте, но учитывает только фактически проведённые (списанные по клирингу) транзакции, которые обычно обрабатываются банком в течение 1–3 рабочих дней. Вследствие этого push-уведомление о превышении лимита отправляется с задержкой в несколько дней после совершения покупки.
- **Рекомендация:** Уточнить правила учета расходов: для оперативной отправки push-уведомлений в момент покупки следует пересчитывать лимит на основе авторизаций (блокировок сумм) в реальном времени, а по проведенным клиринговым операциям осуществлять последующую сверку и корректировку.
- **Уточняющий вопрос** (Бизнес / Product Owner): Должен ли расчет месячного расхода для целей отправки push-уведомлений осуществляться по операциям авторизации в реальном времени (в момент покупки) или строго по финансовому проведению (клирингу) операции через несколько дней?
- **Варианты ответа:**
  - По операциям авторизации в реальном времени (с последующей корректировкой по клирингу)
    - *Что изменится:* Потребуется изменить функциональное требование Ф-2 для поддержки учета сумм авторизаций и логики их отмены/истечения.
  - Строго по финансовому проведению (клирингу) операций
    - *Что изменится:* Бизнес-цель информирования 'в момент покупки' будет недостижима, задержка push-уведомлений составит до 3 рабочих дней.

### Проверка цитат и отсев находок

Каждая находка проходит детерминированную сверку цитат по тексту документа (нормализация, точное совпадение, затем нечёткое сопоставление с заменой на дословный фрагмент документа). Находки без подтверждённой цитаты отбрасываются.

Цитаты в итоговых нарушениях (у одного нарушения может быть несколько цитат):

- Цитаты, совпавшие с текстом дословно (`verified`): 56
- Цитаты, исправленные по тексту документа (`repaired`): 0
- Цитаты, заменённые текстом требования (`anchored`): 0

Находки (кандидаты в нарушения):

- Отброшено находок без подтверждённой цитаты: 0
- Отброшено на этапе критического пересмотра: 0
- Объединено с другими находками как дубли: 22
- Не подтверждено критиком (цитата только по тексту требования): 0

Баланс кандидатов: всего 59 (правила — 24, проверка каждого требования — 18, проверка набора — 15, сводные находки по матрице покрытия — 1, добавлено критиком — 1) = итоговые нарушения 37 + объединённые дубли 22 + удалённые критиком 0 + неподтверждённые 0. Находки без подтверждённой цитаты (0) отброшены до попадания в кандидаты.
